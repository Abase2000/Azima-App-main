# رحلاتي — واجهة تطبيق العميل (Mobile UI/UX)
### مسؤولية: Person 5 — Mobile App UI/UX

واجهة Flutter كاملة لتطبيق العميل، تعمل حاليًا **ببيانات وهمية (Mock Data)** بحيث يمكن
تشغيلها وعرضها فورًا دون انتظار جاهزية الـ Backend من بقية الفريق.

## الشاشات المنفذة (طبقًا لتوزيع المهام بالضبط)
1. Splash — شاشة البداية
2. Login — تسجيل الدخول (+ نافذة استعادة كلمة المرور)
3. Register — إنشاء حساب
4. Home — الرئيسية (بحث سريع، عروض، رحلات وفنادق مقترحة)
5. Search — بحث موحّد بتبويبين (رحلات / فنادق)
6. Flight Results — نتائج الرحلات مع ترتيب حسب السعر/المدة
7. Hotel Results — نتائج الفنادق مع فلترة بالسعر والمدينة
8. Booking — نموذج بيانات المسافر/الضيف وحساب الإجمالي
9. Payment — اختيار طريقة الدفع (بطاقة / محفظة / عند الوصول) + شاشة نجاح الدفع
10. Booking History — سجل الحجوزات (قادمة / مكتملة / ملغاة) + إلغاء حجز
11. Profile — الملف الشخصي وتعديل البيانات
12. Settings — اللغة، الإشعارات، الوضع الليلي، تسجيل الخروج

## طريقة التشغيل
```bash
flutter create rehlaty_shell
# انسخ محتوى lib/ و pubspec.yaml من هذه الحزمة إلى rehlaty_shell
cd rehlaty_shell
flutter pub get
flutter run
```
لا حاجة لأي Backend الآن — كل الشاشات تعمل ببيانات تجريبية معرّفة في `lib/data/mock_data.dart`.

## نقطة التكامل مع باقي الفريق
كل نداءات الشبكة معزولة في ملف واحد: **`lib/services/api_service.dart`**
كل دالة فيه معلّمة بتعليق `// TODO(Person X):` يوضح:
- الـ Endpoint المتوقع (method + path + body)
- من هو المسؤول عن توفيره (Person 1 / 2 / 3)

عند جاهزية أي API حقيقي، المطلوب فقط استبدال جسم الدالة المقابلة بطلب `http` حقيقي
دون تعديل أي شاشة — لأن كل الشاشات تستدعي `ApiService` فقط ولا تعرف تفاصيل الشبكة.

## ملاحظات معمارية
- `lib/models/` — نماذج بيانات (Flight, Hotel, BookingItem, BookingRecord, User)
- `lib/widgets/` — عناصر واجهة قابلة لإعادة الاستخدام (بطاقات، أزرار، حقول نص)
- `lib/theme/app_theme.dart` — الهوية البصرية الموحدة (الألوان تركواز/ذهبي، خط Cairo)
- `BookingItem` هو نموذج وسيط يوحّد تمرير "رحلة" أو "فندق" إلى شاشة الحجز/الدفع
  بنفس الشاشة والمنطق، بدل تكرار الكود لكل نوع.
